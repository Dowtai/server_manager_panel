# AWG Panel — архитектура и план реализации

Статус: согласованный продуктовый план; технические предложения и открытые вопросы отмечены отдельно.
Дата фиксации: 18 ноября 2026.

## 1. Назначение

Самостоятельная панель управления AmneziaWG по аналогии с 3x-ui: управление VPS, пулами серверов, независимыми AWG instances, их репликами, пользователями и клиентскими профилями.

Веб-панель — основной административный интерфейс. Telegram — пользовательский интерфейс к общему backend API. Бизнес-логика и авторизация не зависят от Telegram.

Установщик, генератор конфигураций и модель данных разрабатываются заново. Существующий проект `../awg-telegram-bot` служит справочным материалом; его установщик и генератор не считаются проверенной основой новой системы.

Этот документ не означает, что описанные функции уже реализованы.

## 2. Зафиксированные решения

- Backend, worker и Telegram-адаптер: Go.
- Экспорт пользователю: только `vpn://`. Экспорт `.conf` не требуется.
- Внутренние конфигурационные файлы AWG на VPS допускаются и необходимы для выбранного способа запуска.
- Пользовательские профили не содержат SSH-реквизитов и не дают административного доступа к VPS.
- Создание пользователей и ключей через приложение AmneziaVPN не поддерживается. Управление выполняет наша система; приложение используется для подключения.
- AWG instance — самостоятельная конфигурация, которая может существовать без серверов.
- Instance назначается всему пулу либо выбранным серверам пула. Один instance может иметь несколько назначений.
- Доступ к генерации профилей задаётся пользователю на уровне конкретного instance.
- Администратор уже в первой версии управляет Telegram ID и их доступами через веб.
- Пользователь внутри системы имеет собственный ID; Telegram ID хранится как внешняя идентичность.
- Первая версия поддерживает доменный endpoint и репликацию instance, но не изменяет DNS через API.
- DNS-записи пользователь меняет вручную в Aéza. API-токены DNS, автоматическое переключение и интеграция с ISPmanager в MVP не входят.

## 3. Доменные сущности

| Сущность | Назначение |
|---|---|
| `ServerPool` | Группа VPS и общие инфраструктурные политики, в том числе firewall |
| `Server` | VPS: адрес управления, SSH-реквизиты, публичные адреса, возможности и состояние |
| `AwgInstance` | Логическая конфигурация AWG, серверная пара ключей, параметры, порт и VPN-подсеть |
| `Placement` | Правило размещения instance: весь пул или выбранные серверы пула |
| `Deployment` | Фактическая реплика instance на конкретном VPS |
| `Endpoint` | Клиентский домен или IP и внешний UDP-порт instance |
| `User` | Внутренний пользователь системы |
| `Identity` | Внешняя идентичность пользователя, например Telegram ID |
| `InstanceGrant` | Право пользователя создавать профили конкретного instance |
| `Device` | Отдельный VPN-peer: владелец, instance, адрес, ключи и состояние |
| `Operation` | Длительная операция с этапами, результатом и повторными попытками |
| `AuditEvent` | Кто и когда изменил права, размещение, конфигурацию или устройства |

### 3.1. ServerPool и Server

Пул хранит общую политику инфраструктуры. Он не владеет серверными AWG-ключами.

Предложение для MVP: один сервер состоит в одном пуле. Это обеспечивает один источник общей firewall-политики. Множественное членство серверов не требуется для взаимного резервирования instances.

SSH-адрес управления и публичные VPN-адреса хранятся раздельно. Переключение VPN-домена не должно менять VPS, на который worker подключается по SSH.

### 3.2. AwgInstance

Instance хранит:

- название и описание;
- версию протокола и совместимый runtime;
- серверную пару AWG-ключей;
- параметры обфускации и необходимые секреты AWG;
- VPN-подсеть, адрес VPN-интерфейса сервера и UDP-порт;
- клиентские настройки: DNS, MTU, AllowedIPs и keepalive;
- endpoint для клиентского профиля;
- желаемую ревизию конфигурации;
- административное состояние.

Instance без deployments сохраняется и редактируется как обычный объект. Пользовательская выдача профилей требует как минимум готового deployment, соответствующего выбранному endpoint.

### 3.3. Placement и Deployment

Placement поддерживает два режима:

1. `all_servers`: все текущие и будущие серверы указанного пула.
2. `selected_servers`: явно выбранные серверы указанного пула.

Целевой набор серверов instance — объединение всех его placements. Пара `(instance_id, server_id)` уникальна: пересекающиеся назначения не создают дубликаты контейнеров.

При изменении состава пула система пересчитывает целевой набор. Добавленный в пул сервер получает instances с назначением `all_servers`. Назначение `selected_servers` автоматически не расширяется.

Перед применением изменений интерфейс показывает создаваемые и удаляемые deployments. Если удаляется deployment, на который направлен endpoint, сначала требуется перенаправить DNS и подтвердить изменение. Удаление VPS из учёта, удаление реплики и удаление instance — отдельные операции.

Пример:

| Instance | VPS-1 | VPS-2 | VPS-3 |
|---|---|---|---|
| Personal | Реплика Personal | Реплика Personal | Реплика Personal |
| Friends | Реплика Friends | Реплика Friends | Не размещён |

VPS-1 и VPS-2 взаимно резервируют оба instance. VPS-3 резервирует только Personal. Роли основного и резервного относятся к instance, а не к физическому VPS.

## 4. Модель ключей

| Ключи | Владелец | Правило |
|---|---|---|
| Серверная пара AWG | Instance | Одна и та же пара применяется ко всем deployments этого instance |
| Клиентская пара AWG | Device | Отдельная пара для каждого устройства внутри instance |
| PSK устройства | Device | Одинаков на всех репликах, обслуживающих это устройство |
| Общие секреты AWG, включая HeaderProtectionKey | Instance | Согласованы на всех репликах и в клиентских профилях |
| SSH-реквизиты | Доступ к VPS | Не связаны с VPN-ключами; одинаковость на VPS не требуется |

Например, Personal использует пару A на VPS-1 и VPS-2, Friends — пару B на тех же VPS. Это две независимые VPN-идентичности на одном физическом сервере.

Перенос instance между пулами и добавление реплики сохраняют его ключи. Новый instance получает собственную пару. Приватные ключи клиентов на VPS не передаются: серверу нужны их публичные ключи и PSK.

Смена серверной пары требует обновления клиентских профилей. Компрометация одной реплики затрагивает серверный секрет всего instance.

## 5. Пользователи и права

`User` имеет внутренний UUID. В `Identity` хранится уникальная пара `(provider, external_id)`, например `telegram / 123456789`. Telegram ID хранится в типе, вмещающем 64-битное значение.

Администратор может заранее ввести Telegram ID в вебе, создать пользователя и назначить ему instances. Пользователь не обязан предварительно запускать бота.

Предлагаемые действия администратора:

- разрешить генерацию профилей instance;
- задать лимит активных устройств на instance;
- снять право на создание новых устройств;
- отозвать отдельное устройство или все устройства пользователя в instance;
- заблокировать пользователя с явным выбором отзыва существующих устройств.

Снятие grant само по себе не должно неявно означать отзыв всех действующих устройств. Для комбинированного действия в панели предусматривается отдельная команда.

Backend проверяет права при каждом запросе независимо от интерфейса. Telegram получает только доступные instances и вызывает те же бизнес-операции, что и веб. Передаваемый Telegram-адаптером контекст пользователя принимается только от аутентифицированного внутреннего клиента, а не из произвольного публичного запроса.

MVP: один административный контур и обычные пользователи. Полноценные роли операторов, организации и мультитенантность не входят в первую версию. Способ первичного создания администратора и веб-аутентификации нужно уточнить до разработки интерфейса.

## 6. Хранение конфигураций и ревизии

PostgreSQL хранит желаемое состояние. Конфигурации собираются из структурированных данных; VPS не является источником истины.

У deployment хранятся желаемая и последняя подтверждённая применённая ревизии, время проверки и ошибка. Успешная передача файла не означает успешное применение.

Долгоживущие секреты, SSH-реквизиты и клиентские приватные ключи хранятся зашифрованными. Ключ шифрования находится отдельно от базы; резервирование и восстановление должны учитывать оба компонента. Предложение: поддержать повторное получение своего действующего профиля, поэтому клиентский приватный ключ сохраняется зашифрованным.

Нужны два уровня изменений:

- обычная ревизия: peer, отзыв устройства, deployment и изменения, не требующие нового клиентского профиля;
- изменение параметров подключения: серверный ключ, внешний порт и несовместимые параметры AWG, которые могут потребовать перевыпуска профилей.

Веб до сохранения показывает необходимость перевыпуска. Простая синхронизация не должна молча менять параметры, уже закреплённые у пользователей.

Ручные изменения управляемых peer и конфигураций на VPS считаются расхождением с БД. Приложение AmneziaVPN не выступает вторым источником изменений.

## 7. Генератор и runtime AWG

Генератор разрабатывается заново по официальным репозиториям и проверяется на согласованных версиях AmneziaVPN. Старые шаблоны `vpn://` не переносятся без проверки.

Основы:

- официальные `amneziawg-go` и `amneziawg-tools`;
- закреплённые совместимые версии исходников, toolchain и контейнерного образа;
- один заранее собираемый образ runtime вместо сборки из GitHub при каждой установке VPS;
- валидируемая модель параметров AWG и отдельный сериализатор `vpn://`;
- сохранение домена в endpoint: генератор не заменяет его заранее разрешённым IPv4;
- клиентский профиль без SSH-реквизитов;
- штатные криптографические примитивы и инструменты вместо собственного протокола или собственной криптографии.

Предложение по размещению: один контейнер на deployment с отдельным сетевым пространством. Точный способ публикации UDP, NAT, маршрутизации и выдачи capabilities подтверждается прототипом. Не полагаться на `--privileged` и общую host-сеть без необходимости.

Порт instance выбирается из `50000–59999` с проверкой и резервированием на целевых VPS. На новом VPS конфликт порта блокирует добавление реплики; порт существующего instance не меняется автоматически. В MVP не вводятся разные внешние порты одного instance на разных VPS.

VPN-подсети выделяются централизованно, по умолчанию разные для разных instances. Перед размещением проверяются конфликты с локальными сетями VPS.

Общие firewall-правила пула — декларативная политика. На каждом сервере итоговые правила учитывают его SSH-доступ, размещённые instances и внешний интерфейс. Система изменяет свои цепочки и правила адресно и не очищает весь firewall VPS.

## 8. Синхронизация и операции

Worker приводит deployments к желаемому состоянию по событиям и периодической сверке.

Пример:

```text
Personal: желаемая ревизия 25
  VPS-1: подтверждена 25 — ready
  VPS-2: подтверждена 24 — syncing
  VPS-3: недоступен       — unreachable
```

После восстановления VPS получает актуальную конфигурацию целиком. Ему не требуется последовательно проигрывать все пропущенные изменения peer.

Операции хранятся в БД: тип, инициатор, объект, этап, статус, попытки, ошибка и время. Повторное выполнение идемпотентно: не создаёт второй контейнер, peer или устройство. Изменения одного instance сериализуются с блокировкой и контролем ревизии в БД. Блокировки только в памяти процесса недостаточны.

Очередь поддерживает восстановление после падения worker и защиту от одновременного исполнения устаревших задач. Состояние Telegram-сообщения не определяет состояние операции. Неудачная доставка профиля не должна создавать новый peer при повторе запроса.

Применение конфигурации: подготовить временный файл, проверить его, применить допустимые изменения без перезапуска интерфейса, сохранить постоянное состояние и подтвердить runtime. Для изменений, требующих перезапуска, предусмотреть отдельный путь. Сценарии ошибки между этапами должны быть восстанавливаемыми.

## 9. Выдача и отзыв устройств

Создание устройства:

1. Backend проверяет grant и лимит.
2. В транзакции резервирует адрес и сохраняет ключевой материал, устройство и задачу синхронизации.
3. Worker применяет изменения на deployments.
4. Профиль выдаётся после подтверждения готового deployment, обслуживающего текущий endpoint.
5. Остальные deployments догоняют ревизию в фоне; интерфейс показывает неполное резервирование.

Один профиль соответствует одному устройству. Повторное скачивание профиля и создание нового устройства — разные операции. Лимит проверяется транзакционно, чтобы параллельные запросы его не обходили.

Отзыв сначала фиксируется в БД, затем применяется на всех репликах. Недоступный deployment может сохранять старый peer: его нельзя считать очищенным до подтверждения. Такой deployment исключается из готовых кандидатов для переключения.

Репликация переносит статическую конфигурацию, но не состояние AWG-сеансов, NAT и TCP-соединений. Переключение VPS не обещает сохранения текущих соединений.

## 10. Endpoint и ручной DNS в MVP

Для первого релиза: один основной endpoint на instance. Для реплицируемого instance используется домен с одной выбранной A-записью. Адресные литералы допустимы для одиночных установок и диагностики, но не обеспечивают DNS-переключение.

Панель хранит домен и отмеченную администратором текущую цель. Реальное состояние DNS проверяется отдельно: ручная отметка не является доказательством публикации записи.

Сценарий переключения:

1. Администратор выбирает готовую актуальную реплику в панели.
2. Панель показывает её IP, состояние и результат проверки.
3. Администратор вручную меняет A-запись в Aéza.
4. Панель позволяет проверить DNS и подтвердить соответствие выбранному IP.
5. При необходимости пользователь переподключает VPN после обновления DNS.

Проверка SSH или наличия UDP-сокета не доказывает работоспособность VPN. Технический прототип должен предусмотреть проверку AWG-рукопожатия и тестового трафика.

DNS-кэш и повторное разрешение домена клиентом влияют на переключение. Фиксированное время восстановления и бесшовный переход не гарантируются. Особенности конкретных версий Android/iOS/desktop подтверждаются испытанием.

Будущая интеграция `DnsProvider` сможет заменить ручное действие. Реализация API Aéza, Cloudflare, ISPmanager, хранение их токенов и автоматический failover отложены.

## 11. Компоненты и стек

| Компонент | Предлагаемое решение |
|---|---|
| Backend API | Go, `net/http` + `chi` |
| Работа с БД | PostgreSQL, `pgx` + `sqlc` |
| Миграции | `goose` |
| Worker | Отдельный Go-процесс, постоянная очередь в PostgreSQL |
| SSH | `golang.org/x/crypto/ssh` |
| Веб-панель | React + TypeScript |
| Telegram | Go-адаптер к backend API |
| Развёртывание | Docker Compose |

Версии зависимостей фиксируются на этапе реализации после проверки совместимости. Redis и собственный агент VPS в MVP не нужны. VPS управляются по SSH.

```text
Веб-панель ─────┐
               ├── Backend API ── PostgreSQL ── Worker ── SSH ── VPS
Telegram ───────┘
```

Backend и worker используют общие Go-пакеты доменной логики. Telegram не обращается к БД напрямую. Backend отвечает за авторизацию, проверку лимитов и создание операций; worker — за применение на VPS.

Отказ панели, worker или БД не останавливает уже работающие VPN-контейнеры. Он временно останавливает управление. Для первого релиза достаточно одного управляющего узла с резервными копиями БД и ключа шифрования.

Предлагаемая структура будущего кода, пока не созданная:

```text
cmd/api/
cmd/worker/
cmd/telegram/
internal/domain/
internal/application/
internal/storage/
internal/awg/
internal/deployment/
internal/transport/http/
internal/transport/telegram/
migrations/
web/
deploy/
```

## 12. Административная веб-панель MVP

Нужные разделы:

- Серверы: подключение, проверка, публичные IP, ошибки, deployments.
- Пулы: состав, firewall-политика, последствия изменения состава.
- Instances: создание без размещения, параметры, endpoint, placements и ревизии.
- Deployments: синхронизация, состояние, проверка, повтор операции и удаление.
- Пользователи: внутренние записи, Telegram ID, блокировка.
- Доступы: матрица «пользователь × instance», лимиты устройств.
- Устройства: владелец, instance, статус, получение профиля и отзыв.
- Операции и аудит: прогресс, ошибки, инициатор и повторные попытки.
- Endpoint: готовые реплики, IP для ручного изменения DNS и проверка записи.

Работа с секретами не должна попадать в обычные логи и сообщения об ошибках. Веб-аутентификация, защита административных запросов и разграничение сервисных учётных данных обязательны для релиза.

## 13. Этапы реализации и критерии готовности

### Этап 1. Проверка нового runtime и vpn://

- Выбрать и закрепить совместимые версии AWG и целевых клиентов.
- Собрать воспроизводимый runtime и новый генератор профилей.
- Проверить два независимых instances на одном VPS.
- Проверить один instance на двух VPS с одинаковыми серверными ключами и peer.
- Проверить импорт и подключение `vpn://` по IP и домену.
- Вручную сменить DNS, переподключить клиент и подтвердить работу второй реплики с прежним профилем.
- Проверить добавление и отзыв устройства, перезапуск контейнера и VPS.

Критерий: подтверждено реальное подключение, а не только корректность JSON или наличие интерфейса. Если доменный профиль не работает на целевых клиентах, исследовать причину до реализации DNS-сценария и большой панели.

### Этап 2. Доменная модель, БД и API

- Схема сущностей и миграции.
- Создание и изменение пулов, серверов и instances.
- Placements и расчёт deployments без дубликатов.
- Внутренние пользователи, идентичности и grants на instance.
- Шифрование секретов, административный вход и аудит.

Критерий: instance существует без VPS, перемещается без смены VPN-идентичности, права не зависят от Telegram.

### Этап 3. Worker и восстановление

- Постоянная очередь, ревизии и последовательное применение.
- Установка, обновление, удаление и сверка deployments.
- Повтор после таймаута, перезапуска и частичного выполнения.
- Отзыв устройств на доступных и временно недоступных репликах.

Критерий: после восстановления VPS приходит к актуальному состоянию; повтор задачи не создаёт дубликаты; отставшая реплика не помечается готовой.

### Этап 4. Административный веб

- Разделы из пункта 12.
- Настройка Telegram ID, доступов и лимитов через веб.
- Прогресс операций, объяснимые ошибки, просмотр последствий изменения размещения.

Критерий: инфраструктурой и доступами можно управлять без команд Telegram и ручных правок БД.

### Этап 5. Telegram и выдача профилей

- Аутентификация адаптера и сопоставление Telegram ID с User.
- Выбор только разрешённых instances.
- Создание устройства, получение `vpn://`, обработка ошибок доставки без повторного создания peer.
- Проверка лимитов, изоляции пользователей и отзывов на уровне instance.

Критерий: пользователь не может получить профиль запрещённого instance ни через интерфейс, ни прямым запросом; веб и Telegram используют общие операции.

### Этап 6. Ручное переключение endpoint

- Список готовых реплик и их IP.
- Проверка целевой реплики и DNS после ручного изменения в Aéza.
- Отображение расхождения фактического DNS и выбранной цели.

Критерий: администратор может переключить instance между VPS с сохранением клиентского профиля после повторного разрешения домена клиентом.

### Этап 7. Миграция и выпуск

- Инвентаризация существующих установок без их автоматического изменения.
- Отдельный план импорта либо замены старых deployments.
- Учёт того, что старые профили с буквальным IP не становятся доменными автоматически.
- Проверка наличия ключевого материала: если старый клиентский private key не сохранён, восстановить прежний профиль из публичного ключа невозможно.
- Резервное копирование и пробное восстановление БД и секретов.
- Документация установки, обновления и аварийного восстановления.

Переустановка действующих VPS и перевыпуск существующих профилей требуют отдельного согласованного перехода. Этот план не разрешает удалять старую инфраструктуру.
