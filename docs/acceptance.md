# Приёмка на тестовой инфраструктуре

Локальная реализация не равнозначна пройденной приёмке VPN. Не используйте действующие VPS для этого сценария без отдельного перехода.

## Матрица

Зафиксируйте точные версии AmneziaVPN на Android/iOS/desktop, версию Ubuntu и архитектуру двух тестовых VPS, runtime image digest, ревизию кода и дату. В текущей сессии VPS и клиентские версии не предоставлены, поэтому ни один внешний пункт ниже не считается пройденным.

## Сценарии

1. На Ubuntu VPS-A разместить Personal и Friends с разными подсетями/портами. Проверить отсутствие host networking и privileged. Проверить отдельные серверные public keys и отсутствие клиентских private keys в конфигурациях VPS.
2. Personal разместить также на Ubuntu VPS-B. Проверить идентичность ключей, peer, PSK и AWG-параметров. При пересекающихся placements на A должен остаться один контейнер Personal.
3. Направить единственную A-запись `vpn-test.example` на A. Убедиться, что worker проверил AWG handshake и HTTPS-трафик, затем подтвердить DNS в вебе. Проверить отрицательный сценарий: один SSH или сокет не разрешает выдачу профиля при ошибке probe.
4. Пользователю 1 выдать Personal с лимитом 1, пользователю 2 — Friends с лимитом 0. Привязать Telegram ID через веб. Убедиться, что невыданный instance нельзя получить ни через callback, ни прямым API. Создать два устройства с разными ключами и проверить одновременное подключение.
5. Получить `vpn://` для каждого целевого клиента. Проверить импорт, подключение по буквальному IP на отдельном тестовом instance и по домену; проверить DNS внутри туннеля, доступ к сайтам и перезапуск клиента. Не считать roundtrip JSON доказательством импорта.
6. Вручную переключить A-запись с A на B. Подтвердить DNS в панели, переподключить клиент и проверить прежний профиль. Зафиксировать фактическое время сходимости DNS и поведение каждого клиента; бесшовность не обещается.
7. Отключить SSH на B, добавить устройство на актуальной A. Проверить выдачу после подтверждения A, пока B помечена отставшей. Вернуть B и проверить полную синхронизацию.
8. Повторить при отзыве устройства. До подтверждения B нельзя считать отзыв завершённым на B. Проверить невозможность AWG-рукопожатия отозванным профилем на обеих репликах.
9. Перезапустить контейнер, каждый VPS и worker во время операций. Проверить восстановление постоянного файла, актуальную ревизию, NAT, SSH firewall и отсутствие повторных peer/контейнеров. Проверить загрузку отдельного systemd unit с SSH-политикой до запуска сети.
10. Занять нужный UDP-порт другим процессом/контейнером; создать конфликтующий маршрут/сеть Docker. Проверить отказ установки без изменения порта существующего instance и без удаления чужой инфраструктуры.
11. Проверить ошибочный SSH fingerprint. Проверить сбой между записью staged config, validation, rename, syncconf и подтверждением. Повтор должен сходиться к последнему желаемому состоянию.
12. Переключить endpoint, удалить placement и дождаться удалённой очистки. Проверить сохранность соседнего instance. Для последнего instance: отозвать все устройства, дождаться подтверждения всех реплик, вывести endpoint из эксплуатации и удалить deployments.
13. Сделать резервную копию и восстановить на отдельном контроллере с исходным ENCRYPTION_KEY. Подтвердить выдачу сохранённого профиля и пробное управление тестовой репликой. Затем проверить отрицательный сценарий с другим ключом шифрования.

## Условие выпуска

Все требуемые платформы должны пройти импорт и реальное подключение. Ошибки доменного профиля исследуются до эксплуатации DNS-сценария. Миграция действующих установок согласуется отдельно; её отсутствие не разрешает переустанавливать существующие серверы.


## Приёмка установщика на чистой Ubuntu

- Выполнить `sudo ./install.sh` из нового клона без `.env`, Go и Node. Проверить вход только с заданной парой логин/пароль.
- Проверить установку с HTTPS 443 и с нестандартным портом 9443. Доверенный сертификат должен соответствовать домену, HTTP — перенаправлять на правильный HTTPS-порт.
- Проверить неуспешный выпуск при неверном DNS или закрытом TCP 80: установщик не объявляет успех и сохраняет секреты для повторного запуска.
- После исправления повторить запуск и проверить неизменность ENCRYPTION_KEY, пароля БД и runtime ID. Потеря `.env` при сохранённом volume должна останавливать установку.
- Перезапустить Caddy/хост, проверить сохранность сертификата и ACME-аккаунта. Проверить продление через staging ACME/тестовый выпуск, не создавая повторные запросы к production CA без необходимости.
- Проверить доставку runtime на два Ubuntu VPS через SSH без registry, включая повтор после разрыва передачи и восстановление локального Docker cache из архива.

Офлайн-тесты `scripts/test_installer.py` заменяют Docker/пакетный менеджер/сеть заглушками; отдельные тесты используют настоящий локальный SSH handshake и валидируют Caddyfile официальным Caddy. Это не заменяет перечисленные испытания Ubuntu/ACME.
