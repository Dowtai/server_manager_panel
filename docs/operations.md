# Эксплуатация

## Секреты и доступ

- PostgreSQL хранит зашифрованные SSH-реквизиты, серверные/probe ключи, приватные ключи устройств и PSK. AES-GCM использует отдельный ENCRYPTION_KEY и контекст ID/назначения. Не меняйте этот ключ без отдельной процедуры перешифрования.
- ADMIN_USERNAME задаёт логин (по умолчанию admin), ADMIN_PASSWORD_HASH — bcrypt-хэш пароля. Веб использует HttpOnly SameSite=Strict cookie и CSRF. SESSION_KEY подписывает сессии; его смена завершает все сессии. Выход удаляет cookie браузера; ранее скопированная сессия остаётся действующей до 12-часового срока или смены SESSION_KEY.
- SERVICE_TOKEN разрешает только пользовательские операции от Telegram. Его компрометация позволяет выдавать себя за зарегистрированных Telegram-пользователей, поэтому храните его только в доверенном адаптере/API.
- Не включайте журналирование HTTP body, SSH stdin и ссылок vpn:// в reverse proxy/мониторинге.

## Состояние worker

Операция создаётся вместе с изменением доменной модели в одной PostgreSQL-транзакции. DB advisory lock сериализует изменения, session advisory lock исключает одновременную работу нескольких worker над одним instance. Remote flock сериализует Docker-операции на VPS. Во время удалённого вызова глобальная транзакция БД не удерживается.

Worker всегда читает актуальную полную конфигурацию. Ревизия, изменившаяся во время SSH, не помечается ready: операция возвращается в очередь. После падения worker сохраняется running-операция, которую можно забрать после истечения одиннадцатиминутной аренды. Завершение старой попытки не подтверждает новую попытку. Таймаут работы — десять минут, включая доставку runtime-архива; число попыток — пять, затем ручной повтор в вебе. Повторное применение адресует тот же deployment/container.

Сверка запускается каждые 60 секунд; повторная проверка реплики ставится после 5 минут без проверки. DNS выбранной цели проверяется в фоне. После простоя worker выдача остановится при устаревшей DNS-проверке. VPN-контейнеры продолжат работу независимо от контроллера.

## Резервное копирование и восстановление

1. Сделайте `scripts/backup.sh /secure/backups` и отдельно сохраните ENCRYPTION_KEY, SESSION_KEY, SERVICE_TOKEN и настройки доставки runtime в защищённом хранилище. Для установки через install.sh сохраните также `.installer/runtime.tar`, `compose.override.yml` и volume `caddy_data` с сертификатами/ACME-аккаунтом. Учитывайте volume telegram; потеря offset может повторить старые сообщения, но стабильные request IDs защитят устройство от дублирования.
2. Проверьте дамп `scripts/verify-restore.sh backup.dump`. Проверка создаёт отдельную БД и удаляет только её.
3. На новом управляющем хосте подготовьте `.env` с исходным ENCRYPTION_KEY. Не запускайте старый и новый Telegram polling одновременно.
4. Поднимите только БД: `docker compose up -d db`. До восстановления не запускайте worker.
5. В пустой БД восстановите `docker compose exec -T db pg_restore -U awgpanel -d awgpanel --no-owner --exit-on-error < backup.dump`. Если БД уже содержит данные, сначала отдельно сохраните её и подготовьте пустую БД; не применяйте `--clean` к рабочей базе вслепую.
6. Запустите API, проверьте вход и расшифровку профиля тестового устройства. Смените SESSION_KEY для завершения старых сессий при аварийном переносе. Затем включите worker: он сверит deployments без переустановки по новым случайным ID.
7. Проверьте тестовый VPS и только после этого Telegram. VPN-трафик на VPS не зависит от адреса контроллера.

## Обновление

Сделайте дамп и отдельную копию секретов, соберите новый app image, выполните тесты и приёмку. Остановите worker и Telegram, обновите API (миграции применяются при старте), затем запустите worker и Telegram. Откат приложения допускается только к совместимой схеме; миграции вниз автоматически не выполняются.

Runtime AWG обновляется отдельно. Текущая реализация сравнивает image digest существующего контейнера и не пересоздаёт его автоматически с другим digest. Для смены runtime используйте тестовый instance, пройдите приёмку, затем плановое снятие/повторное размещение реплик по одной, сохраняя instance keys. Перед удалением текущей endpoint-реплики перенаправьте DNS и подтвердите его.

## Диагностика

`docker compose logs api worker telegram` показывает ошибки без секретов. На VPS управляемые контейнеры имеют префикс `awgp-`, label `awg-panel.managed=true`, файлы лежат в `/opt/awg-panel/<deployment-uuid>/`. Права каталога 0700, конфигурации 0600. Не публикуйте содержимое этих файлов и вывод `awg showconf`.

Ошибка внешнего probe может означать блокировку трафика из сети контроллера, отсутствие TUN/Docker, неверный runtime или недоступность внешнего HTTPS-узла `1.1.1.1`. Наличие SSH и успешного syncconf не заменяет проверку трафика. Ошибка может оставлять VPN доступным для существующих устройств, но выдача профилей будет закрыта до проверки.


## HTTPS и установщик

`install.sh` генерирует конфигурацию один раз и при повторном запуске сохраняет ключи, пароль БД и учётную запись администратора. Не удаляйте `.env` для изменения пароля или домена. В ручном режиме изменение логина выполняется через ADMIN_USERNAME, пароля — через ADMIN_PASSWORD_HASH с новым bcrypt-хэшем. Для завершения прежних сессий также смените SESSION_KEY и пересоздайте API.

Caddy получает сертификат Let's Encrypt через HTTP-01, даже когда панель слушает нестандартный HTTPS-порт. Продление работает внутри Caddy; отдельные cron/certbot не нужны. Требуются сохранённый volume `caddy_data`, корректный DNS, доступный TCP 80 и исходящий HTTPS к ACME CA. Проверяйте `docker compose logs caddy`. Не используйте `docker compose down -v` при обновлении: это удалит БД, сертификаты и другие volumes.

`PUBLIC_URL` должен совпадать с внешним origin, включая нестандартный порт и без завершающего слеша. Порт панели задаётся PANEL_PORT. При ручной смене домена/порта согласованно измените PANEL_DOMAIN, PANEL_PORT и PUBLIC_URL, откройте новый порт, затем пересоздайте Caddy и API. Это изменяет только административную панель; VPN endpoint остаётся отдельной настройкой instance.

В режиме архива worker при отсутствии образа загружает `.installer/runtime.tar` через SSH в `docker load` и проверяет ожидаемый sha256 image ID. Для тестового клиентского контейнера на контроллере используется тот же ID; при очищенном Docker cache образ восстанавливается из архива. Registry в таком режиме не используется. Runtime обновляйте отдельно после приёмки: повторный запуск установщика намеренно сохраняет текущий архив и ID.
